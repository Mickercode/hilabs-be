# hilabs-be

The HiLabs API: NestJS, PostgreSQL, and the database that holds the research design.

HiLabs is a learning platform and a research study. The first pilot tests one claim from the
Human Intelligence Models thesis — that the osmotic phase between Discovery and Tailored
Instruction cannot be skipped — as a two-arm comparison over four weeks.

## Stack

| | |
| --- | --- |
| Runtime | Node 22 |
| Framework | NestJS 12 |
| Database | PostgreSQL 16 |
| Types from the database | Prisma Client 7, via introspection |

## The one rule that matters

**The schema owns the model. The ORM does not.**

`db/schema.sql` carries the research design in its triggers and CHECKs: observations are
append-only, deletes are gated behind an authorised erasure, a companion explanation cannot be
written without citing a real resource, and a GIM hypothesis with a missing signal cannot be
classified as strong. An ORM migration will happily drop all of it.

- Generate the Prisma model **from** the database (`npx prisma db pull`), never the reverse.
- Write migrations as hand-written SQL in `db/migrations/`.
- **Any migration that recreates a table drops its triggers.** Re-run the `DO` block at the foot
  of `db/schema.sql`; `hilabs_observation_tables()` is the single list it iterates.
- Nothing deletes a learner except `hilabs_erase_learner()`. The delete order is a foreign-key
  dependency order and a copy of it in TypeScript will drift.

`db/test_schema.sql` is the guard. CI applies the schema to a throwaway Postgres and runs it on
every push and pull request. It is not optional.

## Structure

```
src/
  main.ts                  bootstrap: Swagger, port
  app.setup.ts             shared config, so tests cannot drift from production
  app.module.ts            composition root
  config/                  typed configuration, validated at boot
  common/                  exception filter, logging interceptor, shared DTOs
  prisma/                  PrismaService, including the erasure call
  health/                  liveness and database readiness
  modules/
    learners/              onboarding, export, erasure (R1, R2, R21)
    discovery/             the six challenges and depth events (R4, R6)
    library/               the curated resources and coverage (R8, R9, R20)
    journey/               steps through the phases, and volition (5.1)
    portfolio/             versioned drafts (R14)
    companion/             logged interventions (R11)
    research/              rating progress, blind-export parity, GIM views (R15, R16, R18)
db/                        schema.sql, test_schema.sql
prisma/schema.prisma       generated by introspection, never hand-edited
```

Every module is `module / controller / service / dto`. Controllers validate and delegate;
services hold the rules; the database holds the invariants.

Request validation is strict: an unknown property is a 400, not something to drop silently.
Onboarding must never quietly accept a field it should not have been sent (R2).

Run `npm run start:dev`, then open `http://localhost:3000/docs` for the API.

## Access

Everything is closed by default. `SessionGuard` is registered globally, so a route added without
thinking about access is protected rather than open — the way round that fails safe. Opening one
takes an explicit `@Public()`.

| Who | How they get an account | What they can reach |
| --- | --- | --- |
| Learner | Creates their own, at sign-up | Only their own record |
| Researcher, rater, admin | `npm run staff:create`. There is no endpoint | The researcher view, and any learner record |

**People create their own accounts and set their own passwords.** The team never holds anyone's
credentials, and the consent on file is the learner's own act rather than something recorded on
their behalf — which is what the Nigeria Data Protection Act expects of consent.

Two rules worth knowing before adding an endpoint:

- **A learner id never comes from a request body.** It comes from the session. Taking it from
  the body would let one learner write into another's portfolio.
- **Signing up is not joining the study.** `study_arm` stays null until randomisation, which
  happens after the baseline task because assignment is balanced on that score. The 60-place cap
  belongs at randomisation, not at the door.

Sessions are a token in an httpOnly cookie; only its SHA-256 digest is stored, so a copy of the
database cannot be used to impersonate anyone. Passwords use scrypt from Node's own crypto
module — no native dependency, so `npm ci` stays a non-event on every platform.

## The task catalogue

`db/seed/tasks.json` is what a learner is actually asked to do: the six Discovery challenges with
their optional extensions, and the five assessment tasks. `npm run db:seed` loads it.

It is the machine-readable instrument of record. The research documents carry the design
reasoning; the text in this file is what reaches a learner, transcribed from them verbatim. The
rubric and the pre-registered predictions are written against this exact wording, so:

- **A change to a task's wording ships as a new `version`, never as an edit to `v1`.** Two
  learners who answered differently worded versions of the same task have not answered the same
  task, and their scores are not comparable.
- Seeding is idempotent, matched on `(kind, code, tier, version)`, and only ever writes to
  `task`. It cannot disturb an observation, so it is safe on every deploy.
- The seed fails if the six required Discovery attempts do not cover all six GIM domains. Section
  5.2 requires that, and a silent gap would mean the pilot was not doing what it says it does.

Tiers: 0 is the required first attempt every learner makes once (R5); 1 and above are optional
extensions, offered once and never pressed. Declining one is not a gap.

## Getting started

```sh
cp .env.example .env          # then fill in DATABASE_URL
docker compose up -d db       # or point DATABASE_URL at your own Postgres
npm ci
npm run db:reset              # applies db/schema.sql
npm run start:dev
```

## Scripts

| Script | What it does |
| --- | --- |
| `npm run start:dev` | API with reload |
| `npm run db:reset` | Drops and recreates the schema, then seeds the catalogue |
| `npm run db:seed` | Loads `db/seed/tasks.json` into `task`. Idempotent |
| `npm run db:test` | Resets, then runs the 35 invariant tests against `DATABASE_URL` |
| `npm run test:e2e` | End-to-end against a real database |
| `npm run staff:create` | Creates a researcher, rater or admin account |
| `npm run db:pull` | Regenerates the Prisma model from the live database |
| `npm run lint` / `npm test` / `npm run build` | As usual |
